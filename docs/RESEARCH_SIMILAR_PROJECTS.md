# Similar projects, and what we can mine from them (2026-11)

Nobody is building quite this: a whole OS where the AI is the system, the human is the intent and the guardrail,
outside information is never instructions, and the AI reaches out when it needs you. But many projects build
pieces of it. This is what's out there and what's worth taking.

Most sources are project READMEs, vendor posts and blogs, not independent reviews. Treat feature claims as the
projects' own.

## The closest projects

| Project | What it is | Closest to us in | Different from us in |
|---|---|---|---|
| **OpenClaw** (MIT, very large community) | An always-on personal agent on your machine. A gateway process, skills as markdown files, file-based memory, a heartbeat that wakes it every 30 minutes, messaging apps (WhatsApp, Discord, Telegram) as its channels | Always on, reaches you through your messaging apps, learns from use, skills in markdown | An app on top of an OS, not the OS. Instructions from anywhere can steer it; security problems reported (malicious community skills, memory poisoning) |
| **aaOS** (Apache 2.0) | "An operating system where AI agents are the native processes and humans are supervisors" | The same framing as ours: the human supervises | Agents as processes, not one AI as the system |
| **AIOS** (research, agiresearch) | A kernel for LLM agents: agent scheduler, context manager, memory and storage managers, "LLM system calls" | The core as a kernel for AI work | A runtime on top of Linux for many agents, not a whole OS for a person |
| **openKylin 3.0** (Chinese desktop distro) | Agents built into the OS (KylinBot); also runs OpenClaw | A real distro with the AI in the OS layer | A desktop with an assistant, not the AI as the system |
| **SUSE Linux Enterprise 16** | An enterprise distro with a built-in framework for AI-assisted administration; stresses auditability, policy boundaries and rollback | Rollback and audit of what the AI changes | Admin assistant for servers |
| **Omarchy** (Arch-based) | An Arch distro shipped with coding agents and a scriptable command line an agent can drive | Arch base, made to be driven by an agent | A developer desktop |
| **llm-os** (MIT) | Every app generated from a prompt; "the prompt is the source code"; capability-based security | Apps made by the AI as needed | Experimental, aims at its own kernel |
| **Astrid**, nanos, MielinOS, MoFA (Rust) | Agent operating systems: agents as isolated WebAssembly "capsules" talking over a typed message bus | Rust, an event bus, organs | Built for many agents, not one person |
| **Thumbless OS**, Google's "neural OS" demo | Screens generated by the model on the fly instead of apps | The interface made for the task | Demos. Thumbless reported constant confirmation prompts as the main problem |

### Screen-and-voice assistants (the "talk about what's on screen" piece)

A whole family of open-source "Clicky-style" assistants appeared in 2026: **heyflitty**, **teachy**, **HeyArro**,
**brah**, **nus-companion**, **KLIP**, **Samuel**, **cue**, and a Linux one, **companion** (Wayland, Whisper).
What they share: hold a key and talk, the assistant sees the screen, and it answers out loud while **pointing at,
drawing on, or flying a cursor to** the thing it means. Some click and type for you; cue runs fully local
(whisper.cpp plus a local vision model).

## What to mine

Ranked by how much each would add to LinuxAI for the work it takes.

1. **Undo for what the AI changes (from SUSE).** Before a plan changes the system, take a filesystem snapshot
   (btrfs/snapper on the installed system) and record it in the journal, so "undo that" is one step. Fits the
   assess step: consequences and "how to undo" are already required; this makes undo real.
2. **A heartbeat checklist (from OpenClaw).** Every so often the mind reads a short markdown checklist you can
   edit (`HEARTBEAT.md`: things to keep an eye on), checks it against what changed, and does nothing if nothing
   did. Our rules cover events; this covers "keep an eye on" things that have no event. Cheap when idle.
3. **Your messaging apps as reach channels (from OpenClaw).** Telegram, WhatsApp or Signal as two-way channels
   for questions and answers, before (or instead of) our own Android app. Reach already sends through a command;
   the answer path is what's new. Messages from others stay outside information; only yours are answers.
4. **"Show me how" mode (from the screen assistants).** Besides doing the job, the AI can guide you: a ghost
   cursor flies to the button and the voice says what to do, for things you want to learn or do yourself. Our
   `point` is most of it already.
5. **Hold-to-talk on a hotkey, and a wake word (from the screen assistants).** Hold a key (or a phone button) to
   talk, release to send; later a wake word.
6. **A local vision model for the screen (from cue).** Look at screenshots on the machine when it's private or
   offline; the cloud model when it needs to be better.
7. **Keep the AI's standing context small (from OpenClaw's lesson).** Users report 40,000-50,000 tokens of fixed
   overhead per request on long-running installs. Our approach (playbooks fetched by category, cases on demand)
   avoids that; keep it that way and measure it.
8. **Sandboxing add-ons (from Astrid and llm-os).** When outside skills or organs arrive, run them in a
   WebAssembly sandbox with only the capabilities they're given. Not needed until we take code from others.
9. **Confirmation fatigue (lesson from Thumbless OS).** Asking about everything wears people out. Our answer is
   already the design: trust learned from conversation, "always" turning into a standing permission, questions
   only on low confidence, new situations, or outside information. Track how often it asks, and make the number
   go down.

## Confirmed by what's out there

- **Skills and playbooks as markdown files** are what the largest project (OpenClaw) settled on too.
- **Outside content as instructions is a real danger.** OpenClaw's reported problems (malicious skills, memory
  poisoning) are exactly what LinuxAI's "information, never instructions" rule prevents.
- **Voice plus pointing at the screen** is where screen assistants converged; we have it inside the OS rather
  than as an overlay app.
